# Multi-tenancy

`BusinessMembership` is the authorization link between a business user and a tenant. A business context is established from the authenticated user's active membership; optional `X-Business-ID` only selects among memberships the user already holds and is rejected otherwise. A request body, query parameter, or guessed route ID never establishes tenant context.

`TenantAccessGuard` resolves the membership and role permissions, then attaches trusted business context. Tenant-resource list, detail, create, update, and delete queries all use that business ID. Create ignores any supplied `businessId` and uses the guard context. Ownership checks for uploaded payment proofs and assets use the same tenant boundary. Driver records contain the trusted business ID and reference customers through a composite `(customerId, businessId)` foreign key, preventing cross-tenant parent assignment at the database boundary. Reservations and their rental payment/deposit ledger rows reference tenant-owned parents through composite foreign keys. Integration tests cover reservation cross-tenant list/read/status/ledger access, guessed IDs, supplied-tenant spoofing, and vehicle links; they also verify financial outflows cannot exceed payment/deposit balances.

Platform users use a separate platform guard. Super Admin does not imply a business membership. Customer identity uses a separate customer account context and customer routes; it cannot access business or platform APIs. Support impersonation is deliberately absent until an explicit, time-limited, audited grant workflow is designed.

New tenant-owned tables must have a `businessId` foreign key, indexes aligned with tenant access patterns, and tenant-scoped repository methods. Each module should add negative cross-tenant tests for every operation before release.

Team list and membership update queries require the guard-established business ID. Guessed membership IDs from another business return not found, and changes to membership role/status plus their audit record commit in one transaction. Owner membership changes are rejected; administrator assignment is Owner-only.

Customer extension requests derive the renter from the authenticated customer account linked during verified-email confirmation, then verify that the rental's customer profile has the same `userId`. The request stores explicit business, rental, customer, and requester relationships. Staff list/review calls scope by the active trusted business; approval locks the pending request and rental, checks reservation and maintenance conflicts, updates the rental and request, and writes audit history atomically. A guessed cross-business rental/request ID is returned as not found.
Notification inbox reads and updates use the tenant membership guard plus authenticated recipient for business accounts, or the customer guard plus authenticated recipient for customer accounts. The browser cannot choose the tenant or recipient. Platform identities do not use tenant/customer notification inbox endpoints.

Inspection evidence downloads require an active business membership, the inspection capability, and an asset link to an inspection belonging to that same business. The file key is generated by the server and resolved only beneath the configured provider root; a guessed cross-tenant asset ID is rejected before storage access.
Global workspace search requires an active tenant membership, derives the business from that membership, and applies each resource's view capability before querying. Every searched model query includes the active business ID; customer, reservation, rental and vehicle results are not returned to roles without the corresponding view permission.
