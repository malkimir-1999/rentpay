# RentPay architecture

RentPay is a TypeScript npm-workspaces monorepo and modular monolith. `apps/web` is a Next.js App Router application; `apps/api` is a NestJS API; PostgreSQL is accessed through Prisma. `packages/contracts`, `packages/config`, and `packages/validation` contain shared API error contracts, validated environment configuration, and validation primitives. Domain code lives in `apps/api/src/modules` and is grouped by platform, identity/access, tenancy, subscriptions, fleet, locations, customers, reservations, finance, rentals, inspections, operations, audit, notification, and storage concerns. Fleet, locations, customer/driver, reservation, finance, rental and inspection services scope reads and writes to the trusted membership business ID, enforce same-tenant relationships, and record meaningful mutations in the immutable audit log.

## Trust boundaries

The browser uses Auth.js Credentials with an encrypted, HTTP-only JWT session cookie (secure in production, same-site Lax, eight-hour maximum). Auth.js exchanges credentials with the API and stores a short-lived API access token in its encrypted session. Before expiry, the web server rotates that token through a single-use refresh endpoint. The Nest API independently verifies token signature, token ID, live session, user status, account type, tenant membership, and capability. The API does not authorize from browser session claims alone and protected API endpoints do not accept ambient cookies.

Browser-driven API calls use the same-origin `/api/backend/*` Next.js route handler. It forwards only the requested path, query, content type, request ID, and explicit bearer authorization to the server-configured `API_URL`; the backend origin is never compiled into public JavaScript. This keeps API host configuration private and avoids browser CORS/loopback assumptions while leaving identity and authorization enforcement in NestJS. Next.js `proxy.ts` adds a fresh per-request CSP nonce and passes it to rendering; this keeps Next hydration working without allowing arbitrary inline scripts and makes rendered pages dynamic.

`BUSINESS`, `CUSTOMER`, and `PLATFORM` account contexts are distinct. Business membership grants tenant context and role-derived capabilities. Platform permissions are independent; a Super Admin does not implicitly gain tenant membership or impersonation. Customer tokens can access customer endpoints only.

## Persistence and consistency

Prisma schema and checked-in migrations are authoritative. Registration creates a user, business, OWNER membership, 30-day trial subscription, settings, verification token, and audit event in one database transaction. Invitations and payment verification also use transactions for state changes and their audit records. `AuditEvent` rows are immutable via a PostgreSQL trigger. Tenant-owned query operations receive the trusted business ID established by the membership guard and explicitly constrain reads/writes/deletes by it. Reservation vehicle/customer/location links and payment/deposit ledger links use composite tenant foreign keys. Availability and reservation creation use a vehicle row lock plus overlap checks; reservation state changes follow a server-enforced transition graph and are audited.

## Runtime services

The API uses request-scoped correlation IDs, structured Pino logs, a global typed error filter, Nest validation, Helmet security headers, CSP, CORS allow-listing, and global plus route-specific rate limits. Development throttling uses in-process storage; production requires Redis-backed throttling. Upload services use a provider interface, content-signature validation, a 10 MiB cap, generated keys, tenant prefixes, and persisted asset ownership. Local storage is for development; an S3-compatible adapter can implement the same contract. Pakistan manual subscription payments separate the provider contract, configured Bank Transfer/Easypaisa/JazzCash instructions, purchasable plans, reference/proof submissions, verification, activation, and audit; no prices or receiving details are fabricated. Notifications separate domain events from channel providers: in-app persistence and email delivery are implemented; WhatsApp/SMS have channel contracts and are not falsely reported as delivered.

The public surface includes server-rendered marketing routes with canonical metadata, Open Graph, FAQ/product structured data, sitemap and robots rules; public business sites are hosted under `/rentals/{businessSlug}`. Public visitors can search tenant-scoped vehicle availability for a date window and submit a rate-limited guest booking request; the API rechecks availability under the vehicle lock, atomically creates/reuses the tenant customer, creates a PENDING public reservation, and audits the request. A business user must still verify and confirm the renter. Private `/app`, `/dashboard`, `/platform`, and `/portal` pages are noindex. Business pages use tenant-scoped API data and mutations pass through authenticated same-origin Next route handlers; the short-lived API credential stays server-side. Reservations support staff-created requests, scoped availability, approval/cancellation transitions, audit and transactional conversion to a rental. Rentals require a clear pre-handover inspection and a completed return inspection, support verified-renter and deposit-gated checkout, conflict-checked extension, and audited damage cases. After return and damage resolution, staff with rental, payment and deposit capabilities can settle once: the transaction records any final rental payment, applies held deposit against the remaining balance, records the remainder refunded, creates a final settlement snapshot, and closes the rental. There is no API to amend a completed settlement. Agreements, signatures, final return comparison and invoices remain future work. Rental payment receipt/refund and security-deposit collection/refund/retention ledgers attach to reservations and remain separate from SaaS subscription billing. The Today operations endpoint returns tenant-scoped live counts using the business timezone for day boundaries; damage counts are permission-gated. It currently covers pickups, returns, overdue rentals, requests, vehicle readiness and unresolved damage, not maintenance, document or finance alerts.

Phase 2 onboarding uses tenant-guarded `/api/business/onboarding` endpoints. Fleet has its own additive vehicle aggregate with tenant-unique registration/VIN, condition, location, mileage, configurable rates, and soft archive. Historical vehicle rows are retained; archived vehicles no longer appear in the active fleet or hosted business listing. Location management supports tenant-scoped CRUD with soft archive and denies archiving while active vehicles remain assigned; archived locations are excluded from fleet assignment choices. Reservation-aware availability excludes overlapping blocking requests, active rentals, and blocking maintenance windows and only presents READY vehicles. Tenant-scoped maintenance work orders can be planned, started, completed or cancelled; service windows are checked under the vehicle row lock, blocking work marks the vehicle MAINTENANCE while active, and Today surfaces due-date/mileage and in-progress counts only to authorized staff. Completion moves the vehicle to PREPARATION or DAMAGED; a formal release-inspection workflow is still pending. Inspection evidence references require tenant-owned FileAsset records and composite tenant FKs; files use the secure provider abstraction. Public plans expose configured plan values only. Contact requests are rate limited and delivered to `CONTACT_EMAIL` through the notification abstraction.
